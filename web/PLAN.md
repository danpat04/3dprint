# web v2 — 프로젝트 중심 모델링 도구

> `3d.danp.at/v2` 에 **새 컨테이너로 따로 올려** 개발하고, 완성되면 기존(`/`, `/draw`,
> `/files`)을 대체한다. 기존 구성은 작업 중 건드리지 않는다.

## 무엇을 만드는가

지금의 `feedback_tool` 은 **정적 조회**에 가깝다 — 뷰어는 뷰어대로, 파일은 파일대로,
피드백은 피드백대로 따로 논다. v2 는 **프로젝트를 중심으로** 이것들을 묶는다.

```
/v2                     최근 변경된 프로젝트 · 새 프로젝트 · 전체 목록
/v2/p/<project>         프로젝트 페이지
                          좌: 모델링(파트) 목록
                          우: 선택한 파트의 3D 뷰
                          - 빌드 요청 (웹에서 모델링 실행)
                          - 피드백 전송 (뷰 위에 덧그림)
                          - 드래프트 (백지 + 클립보드 이미지 붙여넣기)
                          - export STEP 다운로드
```

## 확정된 방향

| 항목 | 결정 |
|---|---|
| 배포 | `/v2` 새 컨테이너. 완성 후 기존 대체 |
| 인증 | **Google OAuth + 이메일 화이트리스트** (공개 도메인이므로 필수) |
| 뷰어 | **자체 three.js 뷰어**. 막히면 ocp_vscode iframe 으로 후퇴 |
| 컨테이너 | build123d + f3d + FastAPI **통합 이미지** |
| 파트 목록 | 자동 탐색 + 폴백으로 시작, 손대는 프로젝트만 매니페스트로 이관 |

## 왜 이 결정들인가

### 인증이 선행 조건인 이유

「웹에서 모델링 요청」은 곧 **임의 코드 실행**이다. `models/*.py` 를 돌린다는 건
서버가 사용자 코드를 실행한다는 뜻이고, 공개 도메인에서 무인증이면 누구나
코드를 실행하고 파일을 쓸 수 있다. 지금은 읽기 전용이라 최악이어도 STEP 유출이지만,
실행이 붙는 순간 성격이 달라진다. **빌드 트리거보다 인증이 먼저다.**

### 컨테이너를 합치는 이유

현재 어느 쪽도 혼자서는 "빌드 → 렌더 → 표시"를 못 한다.

| | viewer | feedback |
|---|---|---|
| build123d / OCP | ✅ | ❌ |
| f3d | ❌ | ❌ |
| FastAPI | ❌ | ✅ |

f3d 는 아예 둘 다 없다 (호스트에서 `uv run` 으로만 돈다).
나눠두면 컨테이너 간 작업 위임이라는 배관이 계속 따라붙는다.

### 자체 뷰어를 택한 이유

ocp_vscode 뷰어는 **전역 상태가 하나**다. 좌측 목록에서 파트를 고를 때마다 서버가
다시 push 해야 하고, 탭을 여러 개 열면 서로 덮어쓴다.
파트별 STL 을 캐시해 브라우저가 직접 로드하면 **빌드 없이 즉시** 전환되고,
여러 파트를 색을 달리해 동시에 볼 수 있으며 모바일에서도 돈다.

## 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| **1** | 통합 컨테이너 + OAuth + 프로젝트 목록/상세 API | 진행 중 |
| 2 | 프로젝트 페이지 골격 + STL 캐시 three.js 뷰어 | |
| 3 | 빌드 트리거 (잡 큐 + 진행 표시) | |
| 4 | 피드백·드래프트를 프로젝트/파트/iter 에 귀속, 클립보드 붙여넣기 | |
| 5 | `/files` 기능 흡수 (시각 로컬 표기·상대 시간·최신순) 후 기존 대체 | |

2 단계까지만 해도 "프로젝트 골라 파트 보고 STEP 받고 피드백 보내기" 가 전부 된다.
3 단계는 그 위에 얹는 기능이다.

## 구조

```
web/

  app/
    main.py            FastAPI 진입점 (root_path=/v2)
    auth.py            Google OAuth + 화이트리스트
    projects.py        프로젝트/파트 탐색
    build.py           빌드 잡 큐          (3 단계)
    static/            프런트엔드
  PLAN.md              이 문서
```

- 포트 **3941** (기존 3939 뷰어 / 3940 feedback 과 공존)
- Caddy 가 `/v2/*` 를 붙여 넘기고 FastAPI 는 `root_path="/v2"` 로 URL 을 생성

## 알려진 위험

**f3d 가 컨테이너에서 렌더될지 미검증.** 호스트에서도 `libEGL warning: failed to open
/dev/dri/renderD128` 을 내며 소프트웨어 렌더링으로 돌고 있다. 컨테이너에는 mesa/libegl
계열이 더 필요할 수 있다. 1 단계에서 **가장 먼저 확인**한다 — 안 되면 렌더는 호스트에
남기고 서버는 결과만 읽는 구조로 후퇴한다.

**파트 목록 규약이 프로젝트마다 다르다.** 24 개 프로젝트가 세 갈래로 갈린다:
`model.py` 단일 / `export.py` 의 `PARTS` / 구형 `parts` 딕셔너리.
한 번에 통일하지 않고 폴백으로 흡수한다.

## 사용자 준비물

1 단계를 마치려면 **Google OAuth 클라이언트**가 필요하다 (내가 만들 수 없다).

1. [Google Cloud Console](https://console.cloud.google.com/) → 프로젝트 생성
2. **API 및 서비스 → OAuth 동의 화면** → 외부 → 앱 이름·지원 이메일 입력
3. **사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID**
   - 유형: **웹 애플리케이션**
   - 승인된 리디렉션 URI: `https://3d.danp.at/v2/auth/callback`
4. 발급된 **클라이언트 ID / 보안 비밀**과 **허용할 이메일 목록**을 알려주면
   `.env` 로 주입한다 (git 에는 올리지 않는다)

## 진행 기록

### 1 단계

**f3d 컨테이너 렌더링 — 해결.** 처음엔 엔진 생성 단계에서 세그폴트로 죽었다.
mesa 소프트웨어 렌더링 라이브러리(`libegl1 libgles2 libgl1-mesa-dri libglx-mesa0
libosmesa6` 등)를 넣으니 기본 백엔드로 렌더된다. `LIBGL_ALWAYS_SOFTWARE=1` 로 고정.
→ 계획의 최대 위험 제거. 호스트로 후퇴할 필요 없음.

**파트 탐색 — 24 개 프로젝트 전부 흡수.** 파트 92 개, 파트 0 개인 프로젝트 없음.

| 규약 | 개수 |
|---|---|
| `export.py` 의 PARTS/parts 딕셔너리 | 14 |
| 실행 가능한 .py 모듈 | 40 |
| exports/ 의 STEP 파일 | 38 |

구형 프로젝트는 `__main__` 가드 **없이** 모듈 최상위에서 `finalize_iteration()` 을
부른다 (`models/CLAUDE.md` 의 예시가 그렇다). 가드만 보면 12 개 이상을 놓쳐서,
`finalize_iteration` 호출 자체를 탐지 조건에 넣었다.

**탐색은 코드를 실행하지 않는다** — AST 파싱으로 딕셔너리 키만 읽는다.
import 하면 그 자체가 임의 코드 실행이 된다.
