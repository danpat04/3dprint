# web v2 — 프로젝트 중심 모델링 도구

> `3d.danp.at/v2` 에 **새 컨테이너로 따로 올려** 개발하고, 완성되면 기존(`/`, `/draw`,
> `/files`)을 대체한다. 기존 구성은 작업 중 건드리지 않는다.

## 무엇을 만드는가

지금의 `feedback_tool` 은 **정적 조회**에 가깝다 — 뷰어는 뷰어대로, 파일은 파일대로,
피드백은 피드백대로 따로 논다. v2 는 **프로젝트를 중심으로** 이것들을 묶는다.

```
/v2                     최근 변경된 프로젝트 · 새 프로젝트 · 전체 목록
/v2/p/<project>         프로젝트 페이지
                          좌: 모델링(파트) 목록
                          우: 선택한 파트의 3D 뷰
                          - 빌드 요청 (웹에서 모델링 실행)
                          - 피드백 전송 (뷰 위에 덧그림)
                          - 드래프트 (백지 + 클립보드 이미지 붙여넣기)
                          - export STEP 다운로드
```

## 확정된 방향

| 항목 | 결정 |
|---|---|
| 배포 | `/v2` 새 컨테이너. 완성 후 기존 대체 |
| 인증 | **Caddy forward_auth + oauth2-proxy** (앱에는 인증 코드 0줄) |
| 뷰어 | **자체 three.js 뷰어**. 막히면 ocp_vscode iframe 으로 후퇴 |
| 컨테이너 | build123d + f3d + FastAPI **통합 이미지** |
| 파트 목록 | 자동 탐색 + 폴백으로 시작, 손대는 프로젝트만 매니페스트로 이관 |

## 왜 이 결정들인가

### 인증이 선행 조건인 이유

「웹에서 모델링 요청」은 곧 **임의 코드 실행**이다. `models/*.py` 를 돌린다는 건
서버가 사용자 코드를 실행한다는 뜻이고, 공개 도메인에서 무인증이면 누구나
코드를 실행하고 파일을 쓸 수 있다. 지금은 읽기 전용이라 최악이어도 STEP 유출이지만,
실행이 붙는 순간 성격이 달라진다. **빌드 트리거보다 인증이 먼저다.**

**구현은 앱이 아니라 Caddy 에 뒀다.** 이 서버에는 서비스가 10 개가 넘는다.
앱마다 OAuth 를 붙이면 그 수만큼 구현·갱신·보안 책임이 생긴다.
`forward_auth` 로 Caddy 가 대행하면 **새 서비스는 설정 한 줄로 보호**되고,
앱은 통과된 요청의 헤더에서 이메일만 읽으면 된다.

  구성: `~/tools/auth/` (oauth2-proxy) + `~/tools/caddy/sites/auth.caddy`
  구글 리디렉션 URI 는 `https://auth.danp.at/oauth2/callback` **하나뿐**이다.
  쿠키 도메인이 `.danp.at` 이라 모든 하위 도메인이 세션을 공유한다.

  앱이 받는 헤더: `X-Auth-Request-Email`, `X-Auth-Request-User`

> 구글 동의 화면은 **테스트 상태로 둔다.** 게시하려면 대표 URL 등 브랜딩이 필요한데,
> oauth2-proxy 가 refresh token 을 쓰지 않고(`refresh:disabled`) 자체 쿠키를 168h
> 유지하므로 7 일 제한의 체감이 없다. 제약은 테스트 사용자 100 명 한도와
> 계정 추가를 두 곳(구글 테스트 사용자 + `emails.txt`)에 해야 한다는 것뿐이다.

### 컨테이너를 합치는 이유

현재 어느 쪽도 혼자서는 "빌드 → 렌더 → 표시"를 못 한다.

| | viewer | feedback |
|---|---|---|
| build123d / OCP | ✅ | ❌ |
| f3d | ❌ | ❌ |
| FastAPI | ❌ | ✅ |

f3d 는 아예 둘 다 없다 (호스트에서 `uv run` 으로만 돈다).
나눠두면 컨테이너 간 작업 위임이라는 배관이 계속 따라붙는다.

### 자체 뷰어를 택한 이유

ocp_vscode 뷰어는 **전역 상태가 하나**다. 좌측 목록에서 파트를 고를 때마다 서버가
다시 push 해야 하고, 탭을 여러 개 열면 서로 덮어쓴다.
파트별 STL 을 캐시해 브라우저가 직접 로드하면 **빌드 없이 즉시** 전환되고,
여러 파트를 색을 달리해 동시에 볼 수 있으며 모바일에서도 돈다.

## 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| **1** | 통합 컨테이너 + 인증 + 프로젝트 목록/상세 API | 진행 중 |
| 2 | 프로젝트 페이지 골격 + STL 캐시 three.js 뷰어 | |
| 3 | 빌드 트리거 (잡 큐 + 진행 표시) | |
| 4 | 피드백·드래프트를 프로젝트/파트/iter 에 귀속, 클립보드 붙여넣기 | |
| 5 | `/files` 기능 흡수 (시각 로컬 표기·상대 시간·최신순) 후 기존 대체 | |

2 단계까지만 해도 "프로젝트 골라 파트 보고 STEP 받고 피드백 보내기" 가 전부 된다.
3 단계는 그 위에 얹는 기능이다.

## 구조

```
web/
  Dockerfile           build123d + f3d + FastAPI 통합
  app/
    main.py            FastAPI 진입점 (root_path=/v2)
    projects.py        프로젝트/파트 탐색
    build.py           빌드 잡 큐          (3 단계)
    static/            프런트엔드
  PLAN.md              이 문서
```

- 포트 **3941** (기존 3939 뷰어 / 3940 feedback 과 공존)
- Caddy 가 `/v2/*` 를 붙여 넘기고 FastAPI 는 `root_path="/v2"` 로 URL 을 생성

## 알려진 위험

**f3d 가 컨테이너에서 렌더될지 미검증.** 호스트에서도 `libEGL warning: failed to open
/dev/dri/renderD128` 을 내며 소프트웨어 렌더링으로 돌고 있다. 컨테이너에는 mesa/libegl
계열이 더 필요할 수 있다. 1 단계에서 **가장 먼저 확인**한다 — 안 되면 렌더는 호스트에
남기고 서버는 결과만 읽는 구조로 후퇴한다.

**파트 목록 규약이 프로젝트마다 다르다.** 24 개 프로젝트가 세 갈래로 갈린다:
`model.py` 단일 / `export.py` 의 `PARTS` / 구형 `parts` 딕셔너리.
한 번에 통일하지 않고 폴백으로 흡수한다.

## 계정 추가

1. Google Cloud Console → OAuth 동의 화면 → **테스트 사용자**에 추가
2. `~/tools/auth/emails.txt` 에 한 줄 추가 후 `docker compose restart oauth2-proxy`

두 곳 모두 필요하다. 하나라도 빠지면 로그인이 거부된다.

## 진행 기록

### 1 단계

**f3d 컨테이너 렌더링 — 해결.** 처음엔 엔진 생성 단계에서 세그폴트로 죽었다.
mesa 소프트웨어 렌더링 라이브러리(`libegl1 libgles2 libgl1-mesa-dri libglx-mesa0
libosmesa6` 등)를 넣으니 기본 백엔드로 렌더된다. `LIBGL_ALWAYS_SOFTWARE=1` 로 고정.
→ 계획의 최대 위험 제거. 호스트로 후퇴할 필요 없음.

**파트 탐색 — 24 개 프로젝트 전부 흡수.** 파트 92 개, 파트 0 개인 프로젝트 없음.

| 규약 | 개수 |
|---|---|
| `export.py` 의 PARTS/parts 딕셔너리 | 14 |
| 실행 가능한 .py 모듈 | 40 |
| exports/ 의 STEP 파일 | 38 |

구형 프로젝트는 `__main__` 가드 **없이** 모듈 최상위에서 `finalize_iteration()` 을
부른다 (`models/CLAUDE.md` 의 예시가 그렇다). 가드만 보면 12 개 이상을 놓쳐서,
`finalize_iteration` 호출 자체를 탐지 조건에 넣었다.

**탐색은 코드를 실행하지 않는다** — AST 파싱으로 딕셔너리 키만 읽는다.
import 하면 그 자체가 임의 코드 실행이 된다.

**인증 — Caddy 로 이관.** 앱에 OAuth 를 넣는 대신 `forward_auth` 로 Caddy 가 대행한다.
서비스가 10 개 넘는 서버라 앱마다 붙이면 그 수만큼 보안 책임이 생긴다.
새 서비스는 `import require_auth` 한 줄로 보호된다.

**1 단계 완료.** 통합 컨테이너가 24 개 프로젝트를 인식하고 `/v2` 로 서빙된다.
시각은 서버가 UTC ISO 로만 내보내고 표기는 브라우저가 로컬/상대 시간으로 그린다
(0 단계 항목을 여기서 흡수).

### 2 단계 — 프로젝트 페이지 + 뷰어

다음 작업. 좌측 파트 목록 / 우측 3D 뷰, STEP → STL 변환 캐시, three.js 뷰어.

### 3 단계 — 빌드 트리거

웹에서 파트 옆 ⟳ 를 누르면 모델 모듈을 실행한다. 로그가 화면 아래에 흐르고,
끝나면 목록·다운로드·뷰가 갱신된다.

**직렬 처리.** OCC 는 스레드 안전하지 않고 빌드는 CPU 를 오래 쓴다. 워커 하나로 충분.

**명령은 서버가 정한다.** 클라이언트가 보낸 문자열을 모듈 경로로 쓰면 임의 코드
실행이 된다. 탐색된 파트 목록에 있는 것만 실행하고, `Part.command` 가 서버 쪽
탐색 결과로만 만들어진다.

컨테이너에서 걸렸던 것:

| 증상 | 원인 | 해결 |
|---|---|---|
| `No module named 'ocp_vscode'` | `models/_lib/iter.py` 가 import 한다 | 이미지에 `ocp-vscode` 추가 |
| `cannot create directories /.cache/f3d` | uid 1000 의 홈이 없어 HOME 이 `/` | `HOME=/home/app` 부여 |

빌드 결과물의 소유권이 `danpat04` 로 나온다 (`user: "1000:1000"` 효과).
기존 feedback 컨테이너가 root 로 파일을 써서 호스트에서 지우지 못하던 문제가 없다.

`show()` 가 뷰어에 연결 못 해 로그 끝에 예외가 찍히지만 `iter.py` 가 감싸 처리하므로
빌드는 정상 종료한다 (종료코드 0).

### 4 단계 — 피드백 · 드래프트를 프로젝트에 귀속

v1 의 문제: 업로드할 때 프로젝트를 **드롭다운에서 골라야** 했고, 백지 스케치는
`models/_drafts/<이름>/` 으로 빠져 어느 프로젝트 얘기인지 알 수 없었다.
(`joint` 드래프트를 찾아 헤매고 refs/ 로 손수 옮겨야 했다. 게다가 컨테이너가 root 로
써서 지우지도 못했다.)

v2 는 프로젝트 페이지에서 올리므로 **프로젝트·파트가 URL 에 이미 있다.**

| | 저장 위치 | 파일명 |
|---|---|---|
| 피드백 (뷰 위 덧그림) | `<project>/feedback/` | `<시각>_<파트>.png` |
| 드래프트 (백지 스케치) | `<project>/refs/` | `<이름>_<시각>.png` |

드래프트를 `refs/` 로 보내는 건 실제 쓰임 때문이다 — 백지 스케치는 설계 입력이라
결국 refs/ 로 옮겨 보관하게 된다. 처음부터 거기 두면 옮기는 단계가 사라진다.

**클립보드 붙여넣기는 Excalidraw 가 기본 지원**한다. 별도 구현이 없다.

구현 메모: WebGL 캔버스는 `preserveDrawingBuffer` 없이는 프레임 직후 버퍼가 비워져
`toDataURL()` 이 빈 이미지를 준다.

### 조립품 색 구분 · 자동 갱신

**색 구분** — 조립품 STEP 은 솔리드가 여럿이다 (드라이어 걸이 assembly = 리브2 +
커넥터 + 보). 하나로 합쳐 단색으로 그리면 어느 조각이 어디인지 안 보인다.
솔리드별로 쪼개 색을 달리하고, 좌측 목록에서 끄고 켠다.

조각이 12 개를 넘으면 나누지 않는다 — `name_tag` 는 양각 글자의 자모가 전부 개별
솔리드라 42 개가 나오는데, 42 가지 색은 오히려 난잡하다.

변환 규칙이 바뀌면 기존 캐시가 낡으므로 매니페스트에 `CACHE_VERSION` 을 넣었다.
(임계값을 12 로 바꿨는데 캐시가 그대로라 42 개가 계속 나오던 것을 이걸로 잡았다.)

**자동 갱신** — `/rev/<project>` 를 4 초마다 폴링해 변경이 있으면 목록과 뷰를
다시 불러온다. 터미널에서 빌드해도 화면이 알아서 바뀐다.

### 5 단계 — 기존 도구 대체

`/files` 는 이미 흡수됐다 (62 개로 일치, 확장자 집합 동일).
`/draw` 도 v2 에 들어왔다. 남은 것은 ocp_vscode 뷰어를 걷어내는 일.

단면·측정을 쓰지 않는 것으로 확인돼 (늘 대화로 요청했다) 뷰어를 폐기한다.

**5 단계 1차 — v2 를 루트로.** `3d.danp.at/` 가 v2 다.

| 경로 | |
|---|---|
| `/` | v2 |
| `/v2` | → `/` 308 (기존 링크 보존) |
| `/files`, `/feedback/*`, `/legacy/draw` | 구 도구 유지 (대조용) |

ocp_vscode 뷰어는 자산 경로가 절대경로라 하위 경로로 옮기면 깨진다. 라우팅만 뺐고
컨테이너는 살아 있다 (`localhost:3939`).

포트를 전부 `127.0.0.1` 로 묶었다. 3939·3940 이 `0.0.0.0` 바인딩이라 **방화벽 설정
하나에 의존해** 인증을 우회할 수 있는 상태였다. 이제 Caddy 를 거치지 않으면 닿지 않는다.

**되돌리기**: Caddyfile 의 `3d.danp.at` 블록만 고치면 된다 (주석 참고).
컨테이너는 아무것도 지우지 않았다.
